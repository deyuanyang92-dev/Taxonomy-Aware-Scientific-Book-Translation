**结论：需再改。** v0.2 的方向已明显纠正，但仍缺少能约束实现的几项关键规则：当前语境如何判义、执行记录如何独立验收、旧接口如何避免绕过新门槛，以及专家修订究竟修改什么。

以下“已解决”指**方案层面已解决**，不代表代码已经实现。严重度按剩余风险评定；“致命”指可能让错误取得自动执行资格。审核全程只读，未修改文件、数据库；未运行完整测试。网页尚未实现，相关安全问题均为设计缺口，实际漏洞**未确证**。

文中 `P` 指 [v0.2 方案](docs/plan_multilingual_terms.md)，代码路径均相对仓库根目录。

## 二、仍可能自动放行错译的路径与新增问题

### 1. 【致命】类群范围不能替代当前用法判断

**依据：** P:36、62。同一章内可以同时出现形态术语、普通用语和对其他类群的比较。假设某西语词仅登记了一个形态学义项，当前出现却是普通用法：库内唯一、中文已核、类群已知、没有否决，四项条件仍可能全部满足。

**改法：** 为自动执行登记“何种使用条件下可复用”，并对当前出现验证。试点可限于已核短语、明确结构位置或逐处确认；类群仅是其中一个条件。不能把“没收录第二义项”当成单义证明。

### 2. 【致命】新规则未与旧执行入口隔离

**依据：**

- `term_presub.py:113–115、165` 可直接读取任意 TSV 执行替换，没有义项、证据或裁定门槛。
- `yiku/yiku/classify.py:64–65` 允许部分来源层级较高的**候选学名**成为 HARD。
- `yiku/yiku/cli.py:203–211` 可直接把条目升为已核并修改中文。

这些行为原来有各自用途，但不能作为 P:33–37 新自动执行资格的替代品。

**改法：** 定义唯一的“本方案自动执行资格”接口。旧 HARD、旧 TSV 和旧 `review apply` 均不自动授予新资格；兼容路径须显式标为候选或未受新闸口保护。

### 3. 【致命】只验证已有日志，会漏掉未记录的术语与错配

**依据：** P:16、76、84 关注“每个自动结果”，却未要求检查所有应处理位置。一处源词没被识别，就不会产生日志；译文仍可能错译而检查全绿。两处同词分别译错，也可能被错误关联到两个看似正确的输出位置。

**改法：** 验收同时检查三个集合：原文应处理位置、实际执行记录、最终输出对应位置。未知／拒判项必须保留待处理状态；“没有执行错误”不能等同于“全书术语通过”。

这仍只能验证受覆盖的术语；未发现的新术语需要独立抽查，不能宣称已由该机制证明正确。

### 4. 【重要】撤销条件只写了源语侧，中文侧仍可失效

**依据：** P:39 主要描述新义项／冲突撤销；P:23、35 依赖已核中文条目。中文条目被否决、改义、缩小范围或更换来源后，源词映射本身可能没有变化。

**改法：** 将中文定名、证据、适用条件及规则版本都纳入依赖。变更后撤销相关自动资格，历史结果标为待重检；冻结快照用于解释历史，不能继续证明当前有效。

### 5. 【重要】数据模型缺少可执行的不变量

**依据：** P:23–26。尚不清楚：

- 一个词形能否保留多个义项候选；
- `forms.scope` 与 `senses.scope` 如何求交；
- 同一义项的多个已核中文如何裁决；
- 否决、通过和范围不同的裁定如何相互作用。

**改法：** 补一页约束和决策表即可，不必增加复杂本体。明确多候选、范围不相容、冲突裁定均阻断；正向裁定不得静默清除否决，撤销否决应有显式记录。

### 6. 【重要】“默认不用模型”与评测路径、成本边界未接上

**依据：** P:10、77。三条路径需要翻译引擎，但未说明引擎、配置、联网与缓存条件；主会话标注金标准也涉及模型使用。“一本书 ≤¥2”是否包含核译、重试和人工成本，**未确证**。

**改法：** 明确该限制针对候选学习还是整条翻译流程；记录引擎与费用范围，人工核查时间单列。否则三路径对照可能同时改变引擎和术语处理方式，无法归因。

## 四、第 13 节网页方案

**静态离线 HTML → 修订文件 → 本地闸口**总体合理，符合网页不作主库的要求。问题集中在修订协议，而非是否需要服务器。

| 审查项 | 问题、严重度与依据 | 最小改法 |
|---|---|---|
| 数据流与操作语义 | **致命。** P:108 的“通过”可能指证据确认、源词映射核定或中文定名核定；“改译名”也可能影响整个义项及所有语言。现有 `review` 仅修改 `terms`，不能表达这些差别，见 `cli.py:188–211`。 | 每个操作必须指定对象、范围和作用。“增加词形”默认候选；“改译名”提交新裁定，显示影响范围，不直接覆盖共享中文记录。 |
| 证据是否足够 | **重要。** P:108 展示标签和裁图，未明确展示义项定义、适用条件及两段证据。专家可能只确认中文熟悉，却未确认源词等义。 | 展示源词→义项和义项→中文两段依据；裁图不足时允许“无法判断／请求补证”，不能强迫通过或否决。 |

更简单的做法是：**先定义并验证修订 JSONL 协议和本地导入闸口，再做一个只编辑该协议的静态表格。** 首版导出包只含几十条指定任务和必要证据。这样既照顾不会命令行的专家，也避免为了网页先建设另一套裁定逻辑。

若以后增加本地服务，仅监听 `127.0.0.1` 还不够：仍须校验请求来源、禁止跨站写入，并限制文件访问范围。这是后续版本要求，不必现在开发。

## 五、开工前必须改的最少清单

1. **改写自动执行条件：** 库内唯一不能代替语境唯一；明确当前出现如何满足使用条件，不满足则拒判。
2. **定义独立验收：** 从原文枚举位置，与执行记录及最终输出对应核对；漏识别、拒判和无法定位不能被记成通过。
3. **封住旧入口绕过：** 新资格由统一接口决定，旧 TSV、HARD、`review apply` 不直接授予资格。
4. **补最小版本与撤销协议：** 稳定 ID、证据／中文／裁定版本、范围与否决规则、运行依赖清单；中文侧失效同样触发重检。
5. **先定网页修订协议：** 操作对象、基础版本、外部建议权限、冲突、幂等、事务和导入预览；加最基本的安全转义、导出字段限制及草稿恢复。
6. **冻结试点：** 明确引擎、成本范围、独立金标准、分母与通过条件；先跑小闭环，全面迁移和网页扩展后置。

**最终判断：需再改。** 上述内容补成明确规则后，可以开工做有限试点；当前还不宜据此实施全库迁移或面向外部专家的自动核定写回。
